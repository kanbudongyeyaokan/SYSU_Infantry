# 电控组代码规范

本文档用于约束 SYSU RoboMaster 电控工程的新增代码风格。目标不是追求复杂封装，而是让代码逻辑清楚、层级明确、接口稳定，让后来维护的人能快速判断“这个功能应该放在哪一层、从哪里调用、怎么测试”。

当前仓库的主工程位于 `SYSU_Infantry/`，采用 STM32F407 + STM32 HAL + FreeRTOS + CMake，核心业务代码按五层目录组织：

```text
0-Middleware_Layer
1-Hardware_Layer
2-Hardware_Driver_Layer
3-Function_Module_Layer
4-Application_Layer
```

## 基本原则

1. 高层可以调用低层接口，低层不得反向依赖高层。
2. 新功能优先放入正确层级，不要为了省事把设备驱动、控制算法和任务调度写在同一个文件里。
3. 应用层任务尽量薄，只做收发、调度和调用功能层接口。
4. 对上车安全有影响的代码必须有失能路径、超时处理或明确的默认安全态。
5. 新增 `.c/.h` 后必须同步更新 `SYSU_Infantry/CMakeLists.txt` 的源文件和 include 路径。

## 分层规范

| 层级 | 目录 | 应放内容 | 不应放内容 |
| --- | --- | --- | --- |
| Middleware | `0-Middleware_Layer` | PID、滤波、Kalman、消息中心、CRC、Shell、错误系统、UI 打包等通用能力 | 具体电机 ID、底盘尺寸、任务创建 |
| Hardware | `1-Hardware_Layer` | MCU 内部外设抽象，如 CAN、USART、SPI、I2C、USB、DWT、Watchdog | 某个具体传感器或电机的业务逻辑 |
| Hardware Driver | `2-Hardware_Driver_Layer` | 外部设备驱动，如 DJI 电机、BMI088/HWT IMU、蜂鸣器 | 底盘/云台/发射机构状态机 |
| Function Module | `3-Function_Module_Layer` | 底盘、云台、发射、INS、裁判、视觉、遥控、功率等功能逻辑 | FreeRTOS 任务创建 |
| Application | `4-Application_Layer` | FreeRTOS 任务、队列收发、决策任务、测试任务 | 底层 HAL 细节、大段控制算法 |

## 命名规范

### 文件命名

- 使用小写字母和下划线。
- BSP 文件建议以 `bsp_` 开头，例如 `bsp_can.c`、`bsp_usart.h`。
- 算法或功能文件使用模块名，例如 `algorithm_pid.c`、`chassis_power_control.c`。
- 不要与 CubeMX 生成的 `Core/Inc`、`Core/Src` 文件同名。

### 文件夹命名

- 使用单词首字母大写、下划线分隔的形式。
- 示例：`Remote_Control`、`Gimbal_Task`、`Motor_Driver`。
- 保持与现有目录风格一致，避免同义目录并存。

### 变量命名

- 普通变量使用 `snake_case`。
- 只在本文件使用的全局变量必须加 `static`。
- 句柄变量建议带类型或用途后缀，例如 `chassis_task_handle`、`Chassis_cmd_queue_handle`。

```c
static uint8_t error_count;
QueueHandle_t Chassis_cmd_queue_handle;
static Djimotor_device_t *chassis_motors[4];
```

### 函数命名

- 使用“模块 + 动作 + 对象”的形式。
- 当前工程中常见形式是首字母大写加下划线，例如 `Chassis_Update_Control()`、`Djimotor_Calc_Output()`。
- BSP 层可使用现有风格，例如 `Can_device_init()`、`Uart_register()`。

```c
void Chassis_task_init(void);
void Chassis_Update_Control(const Chassis_cmd_send_t *cmd);
Djimotor_device_t *DJI_Motor_Init(Djimotor_init_config_t *config);
```

### 类型命名

- 结构体类型以 `_t` 结尾。
- 枚举类型以 `_e` 结尾。
- 回调函数类型使用清晰后缀，例如 `ReceiveCallback_t`、`usb_rx_callback`。

```c
typedef struct {
    float vx;
    float vy;
    float wz;
    chassis_mode_e chassis_mode;
} Chassis_cmd_send_t;

typedef enum {
    CHASSIS_ZERO_FORCE = 0,
    CHASSIS_NO_FOLLOW,
    CHASSIS_FOLLOW_GIMBAL,
    CHASSIS_ROTATE,
} chassis_mode_e;
```

### 宏命名

- 宏使用全大写和下划线。
- 与物理标定相关的宏必须在注释中写明标定来源。

```c
#define YAW_CHASSIS_ALIGN_ECD 1990
#define PITCH_HORIZON_ECD 760
#define FRICTION_WHEEL_TARGET_RPM 6700
```

## 格式规范

- 使用 K&R 大括号风格。
- 操作符两侧留空格。
- 函数参数较多时应拆成结构体。
- 复杂条件应拆出中间变量，尤其是安全判断和模式切换逻辑。

```c
if (cmd->chassis_mode == CHASSIS_ZERO_FORCE) {
    Djimotor_set_status(motor, MOTOR_STOP);
}
```

## 注释规范

### 文件头

新增业务文件建议使用 Doxygen 风格文件头，作者统一写 `SYSU电控组`。

```c
/**
 * @file    chassis.c
 * @brief   底盘功能模块源文件
 * @author  SYSU电控组
 * @date    2026-xx-xx
 * @version 1.0
 *
 * @note    实现底盘运动学、模式处理和电机目标计算。
 */
```

### 函数注释

对外接口必须写清楚用途、参数和调用时机。内部短函数可以少写，但复杂状态机必须写清楚模式切换条件。

```c
/**
 * @brief 处理底盘控制指令
 * @param cmd 决策层下发的底盘控制量
 * @note  仅计算并缓存电机输出，CAN 发送由 Motor_control_task 统一完成。
 */
void Chassis_Update_Control(const Chassis_cmd_send_t *cmd);
```

### 代码注释

- 解释“为什么这么做”，不要重复“这行代码做了什么”。
- 对实车安全相关的魔法数字必须写清物理含义。
- 对历史兼容、临时方案、待重构点，明确写 `TODO` 或 `NOTE`。

## 数据类型与内存

- 使用 `stdint.h` 中的定长类型，例如 `uint8_t`、`uint16_t`、`int32_t`。
- 协议帧、CAN 数据、裁判系统结构体必须显式说明字节对齐。
- ISR 和任务共享变量需要考虑 `volatile`、临界区或队列同步。
- 不要在高频控制循环中频繁 `malloc/free`。

```c
#pragma pack(push, 1)
typedef struct {
    uint8_t sof;
    uint16_t data_length;
    uint8_t cmd_id;
} frame_header_t;
#pragma pack(pop)
```

## 任务与通信规范

当前主控制链路主要使用 FreeRTOS Queue：

- `Chassis_cmd_queue_handle`
- `Gimbal_cmd_queue_handle`
- `Shoot_cmd_queue_handle`
- `Chassis_feedback_queue_handle`
- `Gimbal_feedback_queue_handle`
- `Shoot_feedback_queue_handle`

推荐约定：

1. 决策层发送控制指令时使用 `xQueueOverwrite()`，保证队列里始终是最新指令。
2. 执行任务读取不到新指令时必须进入安全默认态，例如底盘零力矩或速度清零。
3. 反馈队列和命令队列不要混用，结构体类型必须一一对应。
4. `0-Middleware_Layer/Message_Center` 的 Pub/Sub 适合调试、低频或解耦通信；若要接入主控制链路，需要明确桥接关系。

## 电机控制规范

DJI 电机驱动采用“算发分离”：

1. 功能模块调用 `Djimotor_set_target()` 设置目标。
2. 功能模块调用 `Djimotor_Calc_Output()` 计算并缓存 `out_current`。
3. `Motor_control_task()` 周期调用 `Djimotor_Send_All_Bus()` 聚合发送 CAN 报文。

不要在功能模块中直接手写 DJI CAN 控制帧；统一通过 `dji_motor.c` 管理，方便掉线保护、限幅和总线聚合。

## 错误处理规范

使用 `0-Middleware_Layer/Error_System` 提供的宏上报错误：

```c
ERROR_INFO("CHASSIS", "init ok");
ERROR_WARN("CAN", "mailbox full");
ERROR_RAISE("INS", "wait timeout");
ERROR_CRITICAL("MOTOR", "motor offline");
ERROR_FATAL("SYS", "unrecoverable error");
```

注意：

- `ERROR_FATAL` 会触发全车急停逻辑，只能用于不可恢复的严重问题。
- 高频循环中的错误必须限频，避免日志影响实时性。
- 离线检测优先接入 `bsp_wdg`，由看门狗统一判定在线状态。

## CMake 维护规范

新增源码后，需要在 `SYSU_Infantry/CMakeLists.txt` 中同步维护：

- `add_executable()` 或 `target_sources()` 中添加 `.c` 文件。
- `target_include_directories()` 中添加头文件目录。
- 新增第三方库时，标明来源和许可证。

如果只新增 `.md` 文档，不需要修改 CMake。

## 提交前检查

提交前至少确认：

1. 只改了本次任务相关文件。
2. 新增模块已加入 CMake。
3. 任务周期、队列长度、栈大小有明确理由。
4. 上车相关改动有失能路径。
5. 文档中的接口名与源码一致。
